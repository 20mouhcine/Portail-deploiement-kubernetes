# Hardening Kubernetes Workloads and Reliable Operations

This plan outlines the architectural changes to harden Kubernetes workloads generated by the portal and to refactor deployment operations from synchronous API calls to durable, asynchronous background jobs.

## User Review Required
> [!IMPORTANT]
> **Database Schema Changes**: This plan introduces a new `DeploymentJob` entity (table) to track asynchronous operations. Spring Data JPA will auto-create this if `spring.jpa.hibernate.ddl-auto` is set to `update`. Please confirm if Flyway/Liquibase is used or if JPA auto-update is acceptable.
> 
> **Image Registry Allowlist**: I will introduce a hardcoded allowlist in `KubernetesConfig` (or `application.properties`) for allowed image registries. You may need to configure this to match your actual registry.

## Proposed Changes

---

### 1. Database and Job Tracking Entities

To support durable jobs with operation IDs, retry/backoff, idempotency keys, and a clear state machine.

#### [NEW] `DeploymentJob.java` (Entity)
- **Fields**: `id` (UUID - operation ID), `deploymentId`, `operationType` (CREATE, UPDATE, SCALE, DELETE, RESTART), `status` (QUEUED, APPLYING, ROLLING_OUT, READY, FAILED), `idempotencyKey` (String, unique constraint), `retryCount` (int), `errorMessage` (String), `createdAt`, `updatedAt`.
- **Purpose**: Acts as the durable queue and state tracker for all deployment operations.

#### [NEW] `DeploymentJobRepository.java`
- **Purpose**: JPA Repository for `DeploymentJob` to query jobs by status (`QUEUED`, `APPLYING`, etc.) and handle locking/polling.

#### [NEW] `JobOperationType.java` & `JobStatus.java`
- **Purpose**: Enums for the state machine and operation types.

---

### 2. Kubernetes Manifest Hardening

Enhancing `KubernetesDeploymentService` to generate production-ready, secure manifests.

#### [MODIFY] `KubernetesDeploymentService.java`
- **Security Contexts**: Add `runAsNonRoot: true`, `readOnlyRootFilesystem: true`, and drop `ALL` capabilities in the container security context. Add a Pod-level security context.
- **Probes**: Add `livenessProbe`, `readinessProbe`, and `startupProbe` using TCP socket checks on the application port.
- **Service Accounts**: Create a dedicated `ServiceAccount` for the deployment with `automountServiceAccountToken: false` to enforce least privilege.
- **Network Policies**: Generate a default `NetworkPolicy` to isolate the deployment (e.g., deny all ingress except from specific namespaces/ingress controllers, allow egress).
- **Labels & Annotations**: Add ownership labels (`deployed-by`, `project-id`) and immutable digest support.
- **Resource Validation**: Add checks before building the manifest to ensure requested CPU/Memory are within a globally defined allowed range.
- **Registry Allowlist**: Add a check against a configurable list of allowed container registries.

---

### 3. Asynchronous Job Processing

Moving synchronous deployment operations to a background worker.

#### [NEW] `DeploymentJobWorker.java`
- **Purpose**: A Spring `@Scheduled` service that polls the `DeploymentJobRepository` for `QUEUED` jobs.
- **Execution Flow**:
  1. Pick a `QUEUED` job and update status to `APPLYING`.
  2. Execute the corresponding `KubernetesDeploymentService` method.
  3. On success, move status to `ROLLING_OUT` (for create/update/restart) or `READY` (for scale/delete).
  4. On failure, increment `retryCount`. If under max retries, set back to `QUEUED` (with backoff logic based on `updatedAt`). If exhausted, set to `FAILED`.

#### [NEW] `DeploymentJobWatcher.java`
- **Purpose**: A separate scheduled task to monitor jobs in the `ROLLING_OUT` state.
- **Execution Flow**:
  1. Check Kubernetes for Deployment rollout status (comparing desired replicas with available/updated replicas).
  2. If rollout completes successfully, update job status to `READY`.
  3. If rollout times out (e.g., ImagePullBackOff, CrashLoopBackOff), mark job as `FAILED`.

---

### 4. Controller and Service Refactoring

#### [MODIFY] `DeploymentServiceImpl.java`
- Modify `create`, `update`, `scale`, `restart`, and `delete` methods to:
  1. Validate inputs (including resource limits and registry allowlists).
  2. Create a `DeploymentJob` with status `QUEUED` and a unique `idempotencyKey` (e.g., hash of request + timestamp).
  3. Return the `operationId` (Job ID) to the controller instead of waiting for Kubernetes.

#### [MODIFY] `DeploymentController.java`
- Update endpoints to return `202 Accepted` along with the `operationId`.
- Add a new endpoint: `GET /api/deployments/operations/{operationId}` to allow the frontend to poll for the status of the durable job.

---

### 5. Frontend Refactoring

To support asynchronous deployment operations, the frontend needs to handle `operationId` and track job progress instead of assuming immediate completion.

#### [MODIFY] `deployments.service.ts`
- Update methods `create`, `update`, `scale`, `restart`, `delete` to handle responses containing `operationId`.
- Implement a polling mechanism using `getOperationStatus(operationId)` to periodically check the status until it reaches a terminal state (`READY` or `FAILED`).

#### [MODIFY] `deployments-page.ts` & `deployment-card.ts`
- Introduce a state tracking mechanism (e.g., signals) to track active operations for each deployment.
- When an action is dispatched, store the `operationId` and display a localized loading/progress indicator for that specific deployment.
- On job success (`READY`), remove the loading state and rely on SSE/refresh to update the UI.
- On job failure (`FAILED`), display the job's `errorMessage` to the user via toast/alert and stop loading.

## Verification Plan

### Automated Tests
- If unit tests exist for `DeploymentServiceImpl`, update them to verify that jobs are queued rather than blocking.
- Add tests for resource validation and registry allowlist rejection.

### Manual Verification
- Trigger a new deployment from the UI or API and verify that an `operationId` is returned immediately.
- Inspect the generated Kubernetes `Deployment` YAML to confirm the presence of probes, security contexts, and the dedicated service account.
- Test a failure scenario (e.g., invalid image) and verify the job transitions to `FAILED` after retries.
